# Dynamic Agent Routing Requirements

## Overview

Users often name profiles by the capability they want rather than a provider brand. A task can use a profile named Frontier for planning and one named Balanced for execution. The dynamic profile selects Claude, Codex, OpenCode, or another provider from an ordered list of complete agent profiles.

## Requirements

### REQ-AGENTS-DYNAMIC-AGENT-ROUTING-001: Dynamic Agent Routing

**Intent:** Users often name profiles by the capability they want rather than a provider brand. A task can use a profile named Frontier for planning and one named Balanced for execution. The dynamic profile selects Claude, Codex, OpenCode, or another provider from an ordered list of complete agent profiles.

#### Acceptance criteria

- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.1:** Kandev always registers one built-in virtual agent family with canonical ID `dynamic` and display name Dynamic. It cannot be disabled or uninstalled, does not expose a CLI command, and is not probed as a concrete inference agent. Profiles created under it have kind `dynamic`.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.2:** Agent settings can create a dynamic profile with a user-defined name, description, icon, and availability scope.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.3:** A dynamic profile references existing concrete agent profiles. It never copies or merges their credentials, environment, model, ACP options, flags, permissions, passthrough behavior, or MCP configuration.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.4:** A dynamic profile's candidate list can reference only concrete, launchable profiles. It cannot reference itself, another dynamic profile, or a rich Office identity in the first version. An Office identity's separate `execution_agent_profile_id` binding can reference a concrete or dynamic profile.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.5:** The profile name is the only capability label. Users can create profiles such as Frontier, Balanced, Economy, Review, or Security Review. Kandev stores no class or tier field and assigns no semantics to those names.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.6:** Each profile has an ordered candidate list. A candidate identifies one concrete profile and stores separate transient-error and hard-error policies. Each class can wait for a trusted near reset, retry the same candidate with bounded exponential backoff, then either skip the candidate or stop.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.7:** A concrete profile with `AutoFallback=true` is not an eligible dynamic candidate. The conductor is the only owner of cross-candidate fallback. An explicit `FallbackModel` remains part of the concrete profile's start-model policy. It does not advance the dynamic candidate list, and turn attribution records the model that ran.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.8:** Dynamic profiles and their concrete candidates participate in the existing profile-in-use dependency dialog. A dependency lookup failure blocks the change. Otherwise, the user can cancel or explicitly confirm deletion or disabling. Confirmed changes keep durable bindings unchanged: stale selected profiles fail closed, while stale or disabled candidates become ineligible and another configured candidate can be selected.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.9:** When a standalone dynamic-profile save completes while other profiles change, every unrelated profile shall retain its latest accepted state, including additions, updates, and removals. Every unrelated valid picker option shall remain available with its accepted label, enabled state, and revision, including options whose owner is temporarily absent from Agent settings. Desktop and phone shall share this behavior. A failed save shall not publish a replacement profile collection.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.10:** A failure shall be charged only to the route generation and candidate that produced it. When the route has already recorded a successor while the predecessor execution still serves the session, a later failure of that predecessor execution shall not open the successor's circuit, advance the route, or change its generation or candidate.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.11:** A route action submitted for a session whose selected profile is not dynamic shall be rejected as a validation error that names the reason. It shall not change session or route state and shall not be reported as an internal failure.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.12:** When a resumed or prepared runtime for the route's claimed execution is ready and waiting for input, the claimed route generation shall become active, whether the process-start callback or the resume-ready path observes it first. A cancelled session, a different execution, or a stale generation shall leave the route unchanged. A failed durable activation shall return an error to the resume caller while preserving the ready runtime. After storage recovers, admission shall be able to complete that same generation without stopping or replacing the current ready execution. Reconciled admission shall succeed only after both the durable route and its persisted session projection are active for that generation and execution.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.13:** An explicit recovery action shall be able to resume a session whose route is still `starting` with no live runtime, re-claiming the same persisted candidate. A live launch owner, a passive resume without same-generation activation reconciliation, and every other non-active route state shall keep the existing route guard. When an explicit recovery action cannot resume, it shall return an error instead of a success response without an execution. A passive session open shall keep its waiting response.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.14:** The restart orphan-route sweep shall mark `action_required` a session parked in WAITING_FOR_INPUT whose route is still `starting` and whose `executors_running` row is absent. A live executor row, a read error, or a stale generation shall leave the session and its route unchanged.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.19:** A qualifying classified failure that may not advance the route, because the attempt already produced output or effects, shall still open the shared circuit of the candidate that produced it, charged under the same generation and candidate rule as AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.10. The route's generation, candidate, and status and the failed turn's existing recovery surface shall stay unchanged and no successor shall launch; later selections shall skip the open circuit until it recovers. An unclassified failure, or a failure of a superseded generation or predecessor execution, shall open no circuit.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.20:** While the `features.dynamicCircuitBackoffEscalation` runtime flag is enabled, each consecutive qualifying failure of one circuit shall open it for 1, 5, 15, and 30 minutes, then 1, 2, and 4 hours, capped at 4 hours. A failure that arrives while the circuit is still open within its window shall belong to the same incident and shall not advance the count. A failed probe shall advance the count. A successful probe shall close the circuit but keep the count, so the next qualifying failure, including one reported mid-turn, continues the ladder; only a turn on that candidate that completes without a provider error shall reset the count to zero. A reset hint later than the ladder deadline shall win; a reset time Kandev inferred without an explicit provider date shall be capped at 24 hours, while an explicit provider reset time shall not be capped. An owner-release hold shall never be replaced. While the flag is disabled, every open shall use the fixed one-minute backoff extended only by a later reset hint, and persisted failure counts shall be ignored.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.21:** The consecutive failure count shall persist with the durable circuit snapshot on SQLite and PostgreSQL, with deadlines stored in UTC, and a backend restart with the flag enabled shall restore it so the next failure continues the ladder. Upgrading an existing database shall add the count with a zero default without changing existing circuit rows.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.17:** When a workspace enables mid-turn provider failover and a Kanban/task dynamic attempt that already produced output or effects fails with `rate_limited`, `quota_limited`, `provider_unavailable`, `provider_overloaded`, or `model_capacity` whose classification allows fallback, Kandev shall perform the same atomic Try next route action a person can submit, at most once per failed route generation and only after the failed turn has settled. The successor shall receive the bounded continuation package built from durable task state; Kandev shall not resend the failed prompt or replay its tools, and shall not change candidate order. A failure of another attempt or prompt generation, a superseded generation, a repeated delivery, a moved route, or a completed turn before the handoff runs shall not advance the route. When the same classified code fails again on a candidate that already failed in the current chain of automatic handoffs, or no eligible candidate remains, Kandev shall not advance automatically and the session shall keep its existing recovery surface. Unclassified failures, other codes, pre-result-safe failures, Office sessions, and workspaces with the setting off shall keep their existing behavior.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.22:** Each workspace shall store a mid-turn provider failover setting that defaults to off for new and existing workspaces and survives the workspace HTTP, WebSocket, and boot-state round trips; an omitted update shall keep the saved value. Workspace settings shall show the toggle to a workspace manager only while dynamic agent routing is enabled.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.23:** When a workspace enables automatic failed-route retry and a classified `rate_limited`, `quota_limited`, `provider_unavailable`, `provider_overloaded`, or `model_capacity` failure leaves a Kanban/task dynamic route in `action_required` or in `waiting` with no eligible candidate, Kandev shall submit the same Retry route action a person can submit, once for that route generation, through the same route-action transaction and continuation package; it shall not resend the failed prompt or replay its tools. The retry shall run no earlier than one minute after the failure and no earlier than the earliest expiry of an open circuit of a candidate the retry could use, and shall record the route reason `auto_failed_route_retry`. Kandev shall submit at most the workspace's limit of automatic retries between successful turns, and shall not retry again when the same candidate fails with the same code as a failure it already retried. A repeated delivery of the failure, a backend restart, a moved or superseded route generation, a session that is not waiting for input, a held candidate, or a setting turned off before the retry runs shall not submit a second or a stale retry. A pending retry shall survive a backend restart. Every other failure, an Office session, a workspace with the setting off, and every declined or stopped case shall keep the existing recovery surface. A person's Retry on a route waiting with no eligible candidate shall reselect in candidate order. When mid-turn provider failover is also enabled, its automatic Try next shall run first and the automatic retry shall apply only after the route reaches one of these recovery states.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-001.24:** Each workspace shall store an automatic failed-route retry setting that defaults to off and a retry limit from 1 to 3 that defaults to 1, for new and existing workspaces, through the workspace HTTP, WebSocket, and boot-state round trips; an omitted update shall keep the saved value and a limit outside 1 to 3 shall be rejected as a validation error. Workspace settings shall show the toggle and the limit, independent of the mid-turn failover toggle, to a workspace manager while dynamic agent routing is enabled.

### REQ-AGENTS-DYNAMIC-AGENT-ROUTING-002: Repeated unclassified failure fallback

An operator can enable a narrow exception to manual recovery for a task using a dynamic profile.
A streak means consecutive qualifying failures from distinct attempts in one session, workflow step, and concrete candidate.
A matching failure has the same trusted origin, phase, semantic code, and complete diagnostic identity.
An empty normal turn end has no diagnostic, so its identity is a fixed, text-free origin tuple.

#### Acceptance criteria

- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.1:** An absent, null, or disabled policy shall retain manual recovery for unclassified failures. Known transient and hard policies shall retain their behavior.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.2:** An enabled candidate policy shall accept a consecutive-failure threshold from 2 through 10. Invalid settings shall fail validation without changing saved configuration.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.3:** Each qualifying failure below the threshold shall require manual recovery. The policy shall not schedule retries or reset waits.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.4:** At the threshold, Kandev shall select the next eligible configured candidate in order. The session, conversation, and logical profile shall remain unchanged. Exhaustion shall require manual recovery without wrapping to an earlier candidate.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.5:** Every counted failure shall have current, trusted evidence of no output and no effects. Stale, conflicting, duplicate, incomplete, or ambiguous evidence shall never advance the candidate.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.6:** Only terminal provider failures, proven agent-process startup failures, and empty normal turn ends (AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.13) shall qualify. User denials, cancellation, task/repository errors, credential-policy denials, and corrupt resume state shall never qualify.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.7:** A different matching identity shall start a new streak at one. Success, output, effects, classified failure, explicit stop, or a changed step, candidate, logical profile, or profile version shall clear the streak. Repeating the same candidate manually shall preserve the streak. Stale and duplicate events shall leave current state unchanged.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.8:** A restart shall preserve committed counts but shall not schedule work from them. Only a new, independently proven safe failure shall extend a restored streak.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.9:** The optional workflow field `disable_unclassified_fallback` shall default to false. A true value shall veto fallback and clear the streak. Create, update, copy, export, import, synchronization, and step events shall preserve explicit values. An omitted update shall preserve the saved value.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.10:** Policy configuration shall survive settings API and browser read-edit-save round trips. Desktop and phone shall retain the existing recovery actions and route-change presentation.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.11:** Concurrent delivery of one failure shall count once and launch at most one successor. Persistence or workflow-context failures shall stop automatic advancement.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.12:** The exception shall apply only to Kanban/task dynamic sessions. Concrete profiles, utility invocations, and Office routing shall retain existing behavior. An unknown execution scope shall fail closed.
- **AC-AGENTS-DYNAMIC-AGENT-ROUTING-002.13:** When the current candidate's policy is enabled and the step does not veto it, a prompt turn that ends normally (`end_turn`, no error) with current, trusted evidence of no assistant text, reasoning, or tool activity shall count as a qualifying failure. A cancelled, errored, stale, duplicate, or terminal-replay completion shall not count. With the policy absent, disabled, or vetoed, or the step unknown, the completion shall keep its existing behavior and shall not enter manual recovery. A counted empty end shall not be cleared by its own completion or process exit.

#### Exclusions

This extension adds no automatic retry loop, global candidate health penalty, new provider classification, or new settings controls.
Operators configure the policy through the existing settings API and workflow import/API contracts.
Raw diagnostics, credentials, and prompts shall not appear in streak state or route events.
